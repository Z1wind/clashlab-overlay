# 决策记录：为什么选进程外外部覆盖层，而不注入

> 日期：2026-11-23。状态：**已定案执行**（用户已同意先走进程外）。
> 范围：仅覆盖层绘制与触控通路；不涉及规则引擎、研究管线、farm 采集线的既有方案。

## 1. 背景与约束

目标：在雷电模拟器（LDPlayer9，实例 0）窗口上叠加战术标注 HUD，并在同一窗口内提供可交互面板；触控要求能点到游戏按钮。
硬约束：不注入 DLL、不 hook D3D/GL、不读写游戏内存、不改游戏进程；单进程单可见窗口；先求稳、先求可交付。

## 2. 候选方案

### 方案 A：进程内注入 DLL + hook 图形 API（被否）

把自研 ImGui/绘制 DLL 注入雷电或渲染进程，hook `Present`/`SwapBuffers`（D3D11）或 `glSwapBuffers`（GL），在游戏帧上叠加。

### 方案 B：进程外外部覆盖层（选定）

独立进程建自己的透明置顶窗口（GLFW + ImGui，`WS_EX_LAYERED | WS_EX_TRANSPARENT | WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW`），按目标客户区矩形逐帧贴合；不碰游戏进程。触控走 Windows 输入栈：SendInput 主、PostMessage 备、ADB 兜底。

### 方案 C：共享内存/读屏旁路（未启用）

外部进程只读屏（BitBlt/PrintWindow/ADB screencap）+ 共享内存交换标注数据，绘制仍在游戏侧或另起离屏合成；本质上是「只读 + 旁路合成」，不注入但要解决帧同步与显示落点。

## 3. 对比表

| 维度 | A 注入 DLL + hook D3D/GL | B 外部覆盖层（选定） | C 共享内存/读屏旁路 |
|---|---|---|---|
| 可见性 | 直接进入游戏 Present 链，理论上最贴帧、可被独占全屏正确合成 | 独立分层窗口，窗口模式/无边框下可见；独占全屏可能被游戏层盖住（本项目雷电为窗口渲染，未触发） | 取决于合成落点；读屏侧本身不可见，需另配显示层 |
| 稳定性 | 游戏/模拟器升级、图形 API 版本切换即崩或 hook 失效；注入崩溃会带挂宿主进程 | 与游戏进程零耦合，游戏崩不影响覆盖层；自身渲染异常单帧跳过不崩（`runtime.py` try 包裹） | 链路最长（读屏→共享内存→合成→显示），任一环缺文件/坏 JSON 需各自降级 |
| 反作弊风险 | **高**：注入/hook 属于典型外挂行为特征，即便只读不写也易被风控标记；CoC 有 Supercell 封号体系 | **最低**：不进游戏进程、不读内存、不改句柄，外部置顶窗 + 标准 Windows 输入事件，与手动操作的输入形态一致 | 低-中：不注入，但持续抓屏/高频读写共享内存仍有被观察面 |
| 模拟器版本适配成本 | 高：每个 LDPlayer 版本的渲染子窗口类名/API/ Present 地址都要重摸，hook 偏移随版本漂移 | 低：只认 `LDPlayerMainFrame` 与可见后代最大客户区（实测 `RenderWindow/TheRender`），矩形用 `ClientToScreen`+`GetClientRect` 每帧重测，不依赖内部地址 | 中：读屏方式（PrintWindow 对 GPU 渲染常黑帧）需逐版本验证 |
| 触控 | 可在进程内直接发输入，看似顺，但与注入风险绑定 | SendInput 绝对坐标（实测单击均值 9.18/11.52ms 两遍）、PostMessage 入队备选、ADB `input tap` 兜底（~222ms），降级链自动跳转 | 同 B，且多一层共享内存往返 |
| 多开/迁移 | 每实例一套 hook 维护 | 单窗口跟随当前目标；多开只取首个可见实例（已知限制） | 同 B |
| 工程量 | 高：注入器、hook 桩、版本探测、崩溃隔离 | 低：GLFW+ImGui 透明窗已跑通，骨架实测贴合 ≤2px | 中高：帧同步与合成未实现 |

## 4. 最终选择与理由

选 **B 外部覆盖层**，理由按权重排序：

1. **反作弊风险最低**：不进进程、不读内存、不 hook，符合「先不碰游戏」的底线，避免为了一层标注把账号暴露给风控；
2. **与模拟器版本解耦**：只靠窗口矩形与标准 Win32 样式，LDPlayer 小版本升级不需要重摸内部结构；
3. **稳定性边界清晰**：覆盖层崩溃不拖垮游戏，缺文件/坏 JSON 走 `data.py` 降级空壳，渲染异常单帧跳过；
4. **交付路径已实测**：透明/穿透/置顶/双模式同帧切换/触控三条通道均有取证（见 `docs/overlay_evidence.md`），不需要再开注入工具链。

附加理由（双屏场景）：本机主屏 `(0,0)-(1920,1080)` 是用户正常使用区，外接屏 `(1920,0)-(3840,1080)` 放模拟器。进程外方案只在跟随目标的外接屏区域合成，不会向主屏扩散；注入方案的 Present hook 随模拟器窗口走，窗口挪到任意屏都可能把绘制带到主屏，反而违反「主屏不被遮挡」的约束。补充：进程外方案可精确裁到渲染客户区（窗口严格等于客户区矩形，不铺满屏幕），注入方案随游戏窗口整体出现，做不到这层裁切。

A 被否的核心不是技术做不到，而是**风险收益不成正比**：换来的贴帧收益在 2D 策略标注上用不上，却把封号与版本漂移两个长期成本背在身上。C 的链路长度与帧同步成本在本阶段没有对应的需求支撑。

## 5. 什么情况下才会改方案（触发条件）

满足任一条件时，重新评估 A/C，而不是现在预埋：

1. 雷电切到**独占全屏**模式，外部分层窗口被游戏层整体盖住、标注不可见，且无法用窗口化/无边框替代；
2. 外部窗口在目标分辨率/DPI 下持续错位，且每帧矩形跟随 + dx/dy 偏移补偿仍修不平；
3. SendInput/PostMessage/ADB 三通道全部失效（如模拟器升级改了输入映射），且没有免注入的替代输入通路；
4. 反作弊政策或风控要求书面变更，或项目需要进程内能力（如读取游戏内状态）而外部读屏无法满足。

触发后先评估 C（只读旁路），最后才评估 A（注入）；A 必须单独做风险评审，不在本版路线内。

## 6. 边界说明

本决策只覆盖「绘制覆盖层 + 下发触控」的通路。研究/识别/farm 采集既有的 ADB 抓帧、规则引擎、LLM 复核不在本次取舍范围内；`clashlab/touch.py` 的三通道降级（sendinput → postmsg → adb）是 B 方案内部的实现选择，不构成注入。
